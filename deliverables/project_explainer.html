1. What the project is

SummarAI turns a raw meeting recording (or a pasted transcript) into three things: a two-sentence summary, a list of typed key takeaways (tagged decision or note), and a list of action items with owner and deadline when stated. Results can be saved into projects, building a searchable history of everything a team has decided across many meetings.

The part built specifically for this course is the agent layer: once a project has saved meetings, a user can ask a natural-language question — "what's overdue?", "who owns the design task?", "draft a recap" — and a single Claude agent answers it by calling tools over the meeting archive, never by guessing.

The business problem this solves: knowledge workers lose hours every week re-reading old meeting notes to answer questions like "did we already decide this?" or "who still owes me that deliverable?". SummarAI keeps that institutional memory queryable instead of buried in a folder of past summaries.

2. Architecture Technical Depth

The system has two layers that run at different times.

2.1 Core pipeline (runs on every upload)

Audio / video file
→
faster-whisper (local, CPU)
→
Transcript
→
Claude Haiku 4.5 + JSON schema
→
Summary / takeaways / action items

If the user uploads a text transcript instead of audio, the Whisper step is skipped entirely.

The key design choice here is structured output: instead of asking Claude for free text and parsing it with regex (fragile), the API call is given a strict JSON schema, so the response is guaranteed to be valid, typed data every time.

    output_config={"format": {"type": "json_schema", "schema": OUTPUT_SCHEMA}},
)

2.2 Persistence and embeddings

When a summary is saved to a project, it's written to Supabase (Postgres) and simultaneously flattened to text and embedded with Gemini embedding-001 (1536 dimensions, matching the pgvector column). The embedding is what makes the meeting findable later by the agent's search_meetings tool.

create table summarizations (
  id uuid primary key default gen_random_uuid(),
  project_id uuid references projects(id),
  meeting_title text, summary text,
  key_takeaways jsonb, action_items jsonb,
  embedding vector(1536),  -- pgvector column
  created_at timestamptz default now()
);

create function match_summarizations(
  query_embedding vector(1536), match_project_id uuid, match_count int
) returns table (..., similarity float)
language sql stable as $$
  select *, 1 - (embedding <=> query_embedding) as similarity
  from summarizations
  where project_id = match_project_id
  order by embedding <=> query_embedding
  limit match_count;
$$;

<=> is pgvector's cosine-distance operator — smaller distance means more similar, so 1 - distance gives a similarity score from 0 to 1.

3. The agent Technical Depth — Agentic Architecture

POST /api/projects/{project_id}/ask is powered by run_agent() in src/app.py. This is deliberately a single tool-using agent, not a multi-agent system.

Why single-agent, not multi-agent? Multi-agent orchestration adds coordination overhead and failure modes (agents disagreeing, hand-off loops) that are hard to defend live in a demo or explain in Q&A. Every capability we need — search, lookup, listing, drafting — fits as a tool the one agent calls, not a separate autonomous agent. The mental model stays simple: one agent, one loop, a fixed toolbox, a step cap.

3.1 The loop

User question
→
Claude + 5 tool definitions
→
tool_use?
→
backend executes tool
→
result fed back
→
repeat (≤5×)
→
final grounded answer
def run_agent(question, project_id):
    messages = [{"role": "user", "content": question}]
    trace = []
    for step in range(MAX_AGENT_STEPS):       # guardrail: hard step cap
        response = client.messages.create(
            model="claude-haiku-4-5", system=AGENT_SYSTEM_PROMPT,
            tools=AGENT_TOOLS, messages=messages,
        )
        if response.stop_reason != "tool_use":
            return {"answer": ..., "sources": ..., "trace": trace}  # done

        # Claude asked for a tool — run it, append result, loop again
        for block in response.content:
            if block.type == "tool_use":
                result = AGENT_TOOL_IMPLS[block.name](project_id, block.input)
                trace.append({"tool": block.name, "input": block.input, "output": result})

3.3 What the user sees

The frontend's "Ask the meeting agent" panel has quick-action chips ("What's overdue?", "What did we decide?", "Draft a recap") and renders a collapsible tool-call trace below the answer — exactly what tools fired, with what arguments. This is what you'd open live in the demo to prove the agent isn't just calling one RAG lookup and dressing it up.

4. Guardrails Anti-hallucination · Anti-loop

Anti agent-loop

MAX_AGENT_STEPS = 5 hard-caps the loop. If the agent hasn't reached an answer in 5 rounds of tool calls, it returns a clear "I wasn't able to reach a grounded answer" message instead of looping forever.

No irreversible actions

Every tool is read-only, except draft_followup, which is a single bounded generation call. There is nothing the agent can do that isn't trivially reversible (nothing is sent, deleted, or modified by a tool call).

Anti-hallucination (grounding)

The system prompt requires every claim to be backed by a tool result and explicitly instructs the agent to say "not found" rather than guess. Verified by an adversarial test in the eval script (see below).

No invented deadlines

find_overdue_action_items only flags items with a real, parseable ISO date. A deadline like "next meeting" is skipped rather than guessed at — the tool would rather under-report than fabricate urgency.

6. Business case & value proposition Business Use Case 20%

The problem: knowledge workers spend hours a week re-reading old meeting notes to answer questions that should be instantly searchable — "did we already agree on this?", "who owns this deliverable, and is it late?". That time is pure overhead: it produces no new decisions, just re-discovery of old ones.

The niche: most meeting tools (Otter, Fireflies, Microsoft Copilot, Zoom's built-in summaries) generate a single-meeting transcript or summary well. Very few let you query across a project's full meeting history with accountability built in (who owes what, what's overdue) — and the ones that do are closed, expensive, enterprise SaaS. SummarAI's differentiation is cross-meeting project memory + action-item accountability, running on an open stack (local transcription, your own Claude/Gemini keys, your own Supabase project) — open, private, and far cheaper to run than an enterprise seat license.

Quantified value: if a 5-person team spends even 20 minutes per person per week hunting through old notes for "what did we decide" — that's roughly 1.6 hours of collective time per week, or about 85 hours a year, recovered by a tool that answers the same question in under 5 seconds.

8. Anticipated Q&A

Why a single agent instead of a multi-agent system?
Multi-agent systems add coordination complexity (hand-offs, disagreement between agents, harder-to-predict failure modes) that's disproportionate for this problem — every capability we need is a stateless, boundable operation, so it fits cleanly as a tool one agent calls. It's also far easier to defend and explain live: there's one loop, one trace, one place guardrails live.
What stops the agent from looping forever or burning unlimited tokens?
MAX_AGENT_STEPS = 5 in src/app.py hard-caps the loop. If it hits the cap without a final answer, it returns an explicit "couldn't reach a grounded answer" message rather than continuing.
What stops the agent from hallucinating an answer?
The system prompt requires every claim to be grounded in tool output and explicitly tells the agent to decline rather than guess. We verified this with an adversarial test (a question about something never discussed in any meeting) — the agent correctly said it couldn't find anything, judged by an independent LLM-as-judge call in evaluate_agent.py.
Why Claude Haiku and not a larger model?
Haiku is fast and inexpensive, which matters for an agent that may call itself multiple times per question (each loop iteration is a full model call). The structured-output schema and the tool-calling API do the heavy lifting on reliability, so a smaller model is sufficient for both extraction and tool orchestration.
Why Gemini for embeddings instead of an Anthropic embedding model?
Anthropic doesn't offer an embeddings API — Claude is chat/completion only. Gemini's embedding-001 was chosen because it's free to start and produces 1536-dimensional vectors, which we standardised on for the pgvector column.
What happens if a meeting is saved without an embedding (no Gemini key set at save time)?
The save still succeeds — embedding failures are caught and logged, not fatal — but that meeting won't show up in search_meetings until it's back-filled. embed_existing.py finds every row with a null embedding and embeds it after the fact.
How do you know the frontend-backend integration is real and not mocked?
Every panel makes a real fetch call to a FastAPI route backed by Supabase and the Anthropic/Gemini APIs — there's no hardcoded response anywhere in index.html. The visible tool-call trace in the Ask panel is itself evidence: it's the literal sequence of backend function calls made for that specific question.
What's the weakest part of the system, honestly?
The core transcription pipeline has no speaker diarization, so when nobody is named in the transcript, action-item owners are left blank rather than guessed — this caps how many action items can be attributed to a specific person. The agent layer inherits this: if the underlying meeting data doesn't have an owner, no tool can recover one.
How would you scale this beyond one team / one Supabase project?
The current design uses a single Supabase project shared via anon key — fine for a course MVP, not for multi-tenant production. The next step would be per-organisation auth and row-level security keyed to a real user/session rather than a shared anon key.
